# Contract Packet — N42.1: Carry-to-delivery motion path (ascend → traverse → release)

> Follow-up defect node on top of N42 (`N41-N42-retention-core-force-hold-chute-win.md`,
> §5). Fixes the *path* the claw takes while carrying a held prize to the chute
> release lane, without touching N42's delivery semantics.
> **Status:** Implemented — verified (2026-08-04). Approved and landed in the working tree.
> **Baseline:** `main` @ `3b8bb05` (N36–N40 landed; N41/N42 implementation work
> uncommitted in working tree, preserved).
> **Source:** live-app observation by Eli during N42 usage — a grabbed prize makes
> the claw move *diagonally* toward the chute area, instead of ascending to the
> top of the box, traversing over the chute, and then releasing.
> This packet was contract-only before approval. The implementation now touches
> only the approved coordinator/config/test surface; no dependencies or generated
> evidence artifacts were changed for N42.1.

---

## 1. Observed vs. expected

**Observed:** after a grip holds, the claw lifts and then travels in a straight
diagonal line from the top of the grab position down toward the chute release
lane; the descent toward the release point begins while the claw is still moving
laterally.

**Expected (classic arcade carry):**
1. **Ascend** straight up from the grab point to the top of the box (Y = 2.8).
2. **Traverse** horizontally along the top to the chute lane — Y held at the top;
   no descent during traversal.
3. **Descend** straight down at the chute lane to the authored release position.
4. **Release** (open fingers, drop hold), prize falls through the chute sensor →
   win, per existing N42 semantics.

## 2. Root cause analysis

- **[verified]** `beginLift()` (`src/effects/n7-coordinator.ts:427-435`) is
  correct: it lifts straight up, keeping grab X/Z and moving only Y to
  `liftPosition[1]` (2.8).
- **[verified]** `beginReturn()` (`src/effects/n7-coordinator.ts:438-446`) starts
  a **single** travel leg from the current (lift-top) position directly to
  `N6_PHYSICS_CONFIG.chute.releasePosition` = `[1.05, 1.87, 0.55]`
  (`src/physics/config.ts:113`) with `TRAVEL_RETURN_MS = 700` (line 747).
- **[verified]** `ClawTravelAnimator` (`src/animation/travel-animator.ts`) eases
  a single parameter t across **all three axes simultaneously** (`easeInOutCubic`),
  so Y descends from 2.8 → 1.87 at the same eased rate that X/Z move to the chute
  lane. Result: a straight diagonal path — the observed defect.
- **[verified]** The return target Y (1.87) is below the lift-top Y (2.8), and the
  top of `travelBounds` is `max.y = 2.8` (`src/physics/config.ts:81-86`), so a
  top-height waypoint at the chute lane is inside bounds and geometrically valid.
- **[hypothesis]** No state-machine change is required: the existing `returning`
  state and the `returnReached` completion can remain; only the *leg sequence*
  inside the return needs to be two legs. To be confirmed at implementation time
  against the N7 tests.

## 3. Minimal-change plan

**Files touched (implementation — only after approval):**

1. `src/effects/n7-coordinator.ts` — replace the single-leg `beginReturn()` with a
   **two-leg sequence**:
   - Leg A (traverse): `current` → `[chute X, 2.8, chute Z]` (chute lane at
     lift-top height).
   - Leg B (descent): `[chute X, 2.8, chute Z]` → `chute.releasePosition`.
   - Track the active leg (e.g., a `returnLeg` flag / waypoint target) so
     `returnReached` fires only after both legs complete; reuse the existing
     `positionsMatch` tolerance and `returning` state. The `releasing` state and
     the N42 delivery/win path stay untouched.
2. `src/physics/config.ts` — optionally add a canonical `chute.overPosition`
   waypoint (`[1.05, 2.8, 0.55]`) next to `sensorPosition` / `releasePosition`,
   authored in the same `world/ClawMount` layer (C-03: config is the sole owner of
   physical parameters). No other config changes.

**Diff sketch (n7-coordinator.ts):**

```text
 beginReturn():
-  target = chute.releasePosition                     // single leg, diagonal
+  target = { x: chute.releasePosition[0], y: 2.8, z: chute.releasePosition[2] }
+  returnLeg = 'traverse'                             // Leg A at top height
  ...
 'returning' case:
-  reach releasePosition → emit returnReached
+  reach current leg target → if 'traverse': switch target to releasePosition
+    (returnLeg = 'descent', Leg B straight down); else emit returnReached
```

**What stays untouched:** `src/physics/adapter.ts` (sensor, hold model, delivery
observation), `src/state/**` (no new states), `src/evidence/**` (evidence shape
unchanged), the win/countdown/payout path in `completeDelivery`, prize reset,
collision matrix, fixed-step policy, dependencies. The release point itself stays
`chute.releasePosition` so N42's drop-through-the-sensor fixture is unaffected.

## 4. Contract

1. The carried prize path is L-shaped: ascend to top → traverse horizontally at
   top height → descend vertically at the chute lane → release. **No simultaneous
   Y-descent and lateral movement during the return.**
2. N42 win semantics are unchanged: delivery is still decided by the chute sensor
   intersection; the release position is unchanged; releasing at the lane after
   the down-leg keeps the drop-through-sensor geometry identical.
3. The return remains deterministic under fixed-step (same `ClawTravelAnimator`,
   same eased interpolation per leg; total path is still position-keyframed).
4. The claw may not leave `travelBounds` at any intermediate waypoint.

## 5. Failure results

- `return-diagonal`: any fixed-step sample during the return shows simultaneous
  X/Z change and Y descent.
- `return-traverse-descent`: Leg A changes Y beyond the travel tolerance.
- `return-descent-lateral`: Leg B changes X/Z beyond the travel tolerance.
- `return-waypoint-out-of-bounds`: the traverse waypoint is outside `travelBounds`
  (guard like the existing out-of-bounds throw at `beginReturn`).
- `return-early-complete`: `returnReached` fires before Leg B reaches
  `releasePosition` (run-epoch desync).

## 6. Evidence required

1. Deterministic motion fixture: fixed-step sampling of claw position during the
   return shows (a) Y == 2.8 for the entire traverse leg (within tolerance),
   (b) X/Z constant at the chute lane during the descent leg, (c) completion at
   `releasePosition`.
2. Existing N42 win/no-win fixtures still pass unchanged (carried-delivery win,
   no-win carry, emergent delivery).
3. Live-app check: grab a prize and watch the claw ascend → traverse → descend →
   release with no diagonal segment.
4. Full gate: `npm run typecheck` && `npm run lint` && `npm test` && `npm run build`
   — all green.

## 7. Regression risk + test plan

- **Risk:** N7 coordinator tests (`src/evidence/n7.test.ts`) may assert return
  timing/completion from the single-leg path; the two-leg sequence changes the
  motion shape and total duration split. Mitigation: keep the same total budget
  (`TRAVEL_RETURN_MS` split across legs, see Open Questions) or update the
  affected fixture with a documented reason; never weaken determinism assertions.
- **Risk:** a mid-flight early `returnReached` could skip the release. Mitigation:
  gate `returnReached` on both legs, covered by `return-early-complete`.
- **Test plan:** add one motion fixture (evidence §6.1); keep all N42 evidence
  tests untouched; run the full suite.

## 8. Acceptance criteria (exact repro check)

1. **Repro:** play a run, aim over the prize, grip successfully, carry. Watch the
   claw. **Pass** = claw ascends straight up, travels horizontally along the top
   to the chute lane with **no descent during traversal**, descends straight down
   at the lane, releases; the prize falls into the chute and the win fires.
   **Fail** = any diagonal segment between lift-top and release.
2. **Deterministic check:** in the motion fixture, `max |ΔY|` over the traverse
   leg ≤ travel tolerance and `max |ΔX|/|ΔZ|` over the descent leg ≤ travel
   tolerance.
3. Full gate green (evidence §6.4).
